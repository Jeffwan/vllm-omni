  Important Finding: Multi-Node is Work-in-Progress

  After reading the code carefully, I found a critical detail:

  - --stage-id is parsed in CLI (serve.py:114-178) and validated (requires -oma
  and -omp), but the stage filtering logic is not fully wired in
  AsyncOmniEngine. Currently, _resolve_stage_configs() loads ALL stages
  regardless of --stage-id.
  - --headless is deprecated — calling it raises RuntimeError
  (serve.py:375-391).
  - There is an OmniCoordinator infrastructure (omni_coordinator.py) built with
  ZMQ ROUTER/PUB sockets for stage registration, heartbeats, and discovery — but
   it's not yet activated in the main engine loop.

  So the doc describes the intended design, but the actual multi-node
  per-stage-per-node deployment path is still being built. What does work today
  is:

  Why Ray isn't needed yet

  - Within a stage: vLLM's own distributed_executor_backend="mp" handles TP/PP
  via multiprocessing
  - Across stages: The Orchestrator + ZMQ + Mooncake connectors handle it
  - Multi-node: Mooncake provides the cross-node data plane; the control plane
  (coordinator) is being built with ZMQ, not Ray

  When Ray would be useful

  The planned design (ray_based_execution.md) envisions:
  # Head node
  ray start --head --port=6399
  # Worker node
  ray start --address=<HEAD>:6399

  # Then vllm serve with --worker-backend ray
  # Ray placement groups would assign stages to specific nodes

  Both self.metadata and self.master are passed into the Mooncake library's

  Two URLs, Two Services

  ┌─────────────────── mooncake_master process ───────────────────┐
  │                                                                │
  │   ┌──────────────────────────┐  ┌───────────────────────────┐ │
  │   │  gRPC Master (:50051)    │  │  HTTP Metadata Server     │ │
  │   │                          │  │  (:8080)                   │ │
  │   │  • Control plane         │  │                            │ │
  │   │  • Cluster membership    │  │  • Service discovery       │ │
  │   │  • Replication config    │  │  • Key → node mapping      │ │
  │   │  • Store lifecycle       │  │  • REST API for lookups    │ │
  │   │    (create, close, GC)   │  │  • "Where is this key?"   │ │
  │   └──────────────────────────┘  └───────────────────────────┘ │
  └────────────────────────────────────────────────────────────────┘

  URL: master: "10.90.67.86:50051"
  Config key: master
  Default: 127.0.0.1:50051
  Purpose: gRPC control plane — cluster management, store lifecycle, replication

    coordination
  ────────────────────────────────────────
  URL: metadata_server: "http://10.90.67.86:8080/metadata"
  Config key: metadata_server
  Default: http://127.0.0.1:8080/metadata
  Purpose: HTTP data plane routing — key-to-node lookup so get() knows which
  node
    holds a key

  How they work together

  Stage 0 calls put("kv_cache_req123", data):

    1. Connector serializes data
    2. store.put() contacts Master (:50051 gRPC) to register the key
    3. Master records: "kv_cache_req123 lives on node 10.x.x.1"
    4. Data stored in local memory segment

  Stage 1 calls get("kv_cache_req123"):

    1. store.get() queries Metadata Server (:8080 HTTP):
       GET http://10.90.67.86:8080/metadata?key=kv_cache_req123
       → Response: "node 10.x.x.1, segment offset 0xABCD"
    2. Fetches data from that node over TCP/RDMA
    3. Returns deserialized object

  Master (gRPC :50051) = "manage the cluster and coordinate writes"
  Metadata Server (HTTP :8080) = "find where data lives so readers can fetch it"

  They're both served by the same mooncake_master process (that's why they share
   the same host IP), but they're two separate services on different ports with
  different protocols, handling different concerns. The split allows the read
  path (metadata lookups) to scale independently from the write/control path
  (cluster management) — HTTP is also easier to debug and monitor than gRPC.

  My recommendation: BAGEL-7B-MoT — even though it's larger, because:

  1. It's what our entire doc is about — the multi-node architecture, Mooncake
  connectors, KV cache transfer are all designed around the BAGEL AR→DiT
  pipeline
  2. It already has a bagel_multiconnector.yaml with Mooncake wiring — no config
   work needed
  3. It's the only model with an existing multi-node config
  (bagel_multiconnector.yaml). The TTS/audio models only have single-node
  configs.
  4. The KV cache transfer (the hardest part of multi-node) is specific to
  BAGEL's thinker→dit flow

  If VRAM is truly tight (e.g., only 16GB GPUs), then CosyVoice3-0.5B is the
  smallest, but you'd need to write the multiconnector YAML from scratch and the
   code2wav stage doesn't use KV cache transfer — so it wouldn't exercise the
  Mooncake path.

  Practical suggestion: Use BAGEL-7B-MoT with gpu_memory_utilization: 0.45 per
  stage. On two 24GB GPUs (one per node), each stage gets ~10.8GB which is
  enough for the 7B thinker and the DiT respectively.

❯ If we explicitly use mooncake tcp, but not use sharememory connector. that    
should be ok?                                                                   

⏺ Yes, totally fine. The connector is just a config choice in the YAML —
  Mooncake TCP works on localhost the same as cross-node. Using it consistently
  means:

  1. Same code path in dev and prod — no connector-type mismatch surprises
  2. SharedMemoryConnector is only an optimization for same-node — it avoids
  serialization overhead, but for dev/testing the TCP latency on localhost is
  negligible (~0.1ms)
  3. The KV cache transfer already uses Mooncake (bagel_multiconnector.yaml
  wires both output_connectors and omni_kv_config through mooncake_connector)

  The only trade-off:

  ┌─────────────────┬────────────────────────────┬──────────────────────────┐
  │                 │   SharedMemoryConnector    │ MooncakeStoreConnector   │
  │                 │                            │          (TCP)           │
  ├─────────────────┼────────────────────────────┼──────────────────────────┤
  │ Serialization   │ Skipped for large objects  │ Always                   │
  │                 │ (direct SHM)               │ serialize/deserialize    │
  ├─────────────────┼────────────────────────────┼──────────────────────────┤
  │ Latency         │ ~0.01ms                    │ ~0.1ms                   │
  │ (localhost)     │                            │                          │
  ├─────────────────┼────────────────────────────┼──────────────────────────┤
  │ Extra           │ None                       │ Mooncake Master process  │
  │ dependency      │                            │                          │
  ├─────────────────┼────────────────────────────┼──────────────────────────┤
  │ Matches prod    │ No                         │ Yes                      │
  │ path            │                            │                          │
  └─────────────────┴────────────────────────────┴──────────────────────────┘

  For dev testing, matching the prod path is more valuable than saving 0.09ms.
  Keep Mooncake TCP everywhere — it's one less variable when debugging.

  The bagel_multiconnector.yaml already does this (no SharedMemoryConnector
  configured), so you don't need to change anything.
